## Assumptions (this spec was written without a person to ask)
1. **`onEvent` has the type `EngineEvent`, as the plan says, so it gets no `background` and no `nearest` on `sound` events.** The plan's first test title says "sound, unknown and background decisions with nearest". The engine gives no event for `background` and gives `nearest` only on `unknown`; the overlay gets those from the `segment` message. The plan's interface line and "reuse the existing worker messages" decide for `event`. An app that needs the nearest example of every segment would need a third callback on the `segment` message. This is a cheap addition, but nothing in Tasks 22 and 23 needs it, so it is not built. The test title is changed to what is tested (test E3). If the person who reads this wants the `segment` data in the callback, say so before step 4.
2. **`ears.labels` lists `hum` when a pitch exists.** The plan says "sound names, `background` excluded". `hum` is a taught label with no examples, only a pitch, and Task 22's first-run check must tell that the hum is missing. Without this, `labels` could not show it.
3. **A stored model whose rate differs from the input is ignored only when `sounds` was omitted.** Task 16 does not check the rate of a stored model against the input (the overlay shows a warning). A first-run model was taught on this device at this rate, so a rate change means it is wrong for the new input, and silently using it would give bad recognition in an app that has no overlay. For a shipped model the rule stays.
4. **`hum` patterns stay in the grammar when there is no baseline.** The alternative (drop them at compile time and add them back later) needs a new method on the `Matcher`. Keeping them costs one `if` that already exists in `pushContinuous`.
5. **No `emptySounds()` export.** See the next section.

## Why an optional `sounds` and not `emptySounds()`
The plan allows either. The optional `sounds` is simpler and clearer for these reasons.
- **The sample rate is not known before the microphone opens.** A model carries `sampleRate`, so a public `emptySounds()` would need either a rate argument (which the app cannot know) or a placeholder rate that `listen()` must replace after the microphone opens. A placeholder is a second kind of model that every function must treat specially. With an optional `sounds`, `listen()` builds the empty model itself after it knows the rate, and the model has one meaning everywhere.
- **No new public runtime name.** `test/public-api.test.ts` then pins that `web/index.ts` still exports the same seven runtime names. The plan says that public names make three documents change. With this choice only types are new.
- **The common call gets shorter.** An app that has no shipped sounds writes no line for them.
The cost is a type that is a little looser (`sounds` may be missing). A caller who forgets `sounds` by mistake gets a working but silent app instead of an error. The doc comment says so, `ears.labels` shows an empty list, and the debug overlay shows the model (no labels).

## Findings from reading the code
1. **`classifyVector` crashes on an empty model.** `ranked[0]` is `undefined` and the vector-length check compares with `mean.length` 0. The engine must not call a classifier when the model has no examples. The guard goes in `core/engine.ts` (the one caller), not in `classifyVector`, so the classifier's contract and its tests stay as they are. The guard skips `onSegment` and the `unknown` event too: the `unknown` event needs a `nearest`, and there is no example to be near.
2. **`retrainLabel` for `hum` retrains the whole model and cannot work on an empty one.** It keeps all vectors of the old model (hum has none of its own) and calls `trainVectors`, which throws for no vectors. For `hum` on a model that has no examples there is nothing to train: the result is the old model (empty arrays) with the new pitch. The loo report for no labels is `labels: []`, `confusedPairs: []`, plus the warnings. `looReport` is not called with an empty model.
3. **`retrainLabel` for a sound label already works on an empty model** in the code that was read (the old vectors are an empty list, the new ones are at least five). Step 2 of the tasks proves it with a test and fixes only what the test finds. The model's `sampleRate` is the microphone's, so the `sample-rate-mismatch` warning does not appear.
4. **The baseline reaches the grammar through the rebuild.** `buildEngine` is called on `init`, `replaceSounds`, `record-end` and `record-cancel`, each time reading `sounds.pitch` through `createEngine`. So the only change in the grammar is the removal of the throw.
5. **After the throw is gone, a model can no longer make `createEngine` fail.** The throwaway engines in `listen()` (start, stored model, `importSounds`) still catch a bad mode or a bad pattern, but those do not depend on the model. They stay unchanged (no cleanup in this task). The message "your handlers do not fit this model" can no longer be reached for a model reason; the comment in `listen.ts` is updated.
6. **`replaceSounds` leaves the envelope time axis running while the engine clock restarts.** After `importSounds` the page would see envelope `t0` values that continue from the old session and engine times that start at 0. `toPageTime` needs the two to agree. The change is one call in the Worker's `replaceSounds` case (the same reset that `record-end` and `record-cancel` use). The overlay is re-mounted at import, so it starts a new time axis anyway, which is consistent with the reset.
7. **The page does not see chunks.** The worklet posts them to the Worker over a `MessageChannel`. The page sees `envelope` messages (one per chunk of `WEB_CHUNK_MS`, at 20 ms, with two bins of 10 ms, or none when a chunk completes no bin). Their arrival is the only page-side signal of the audio clock, and it exists in the microphone, `MediaStream` and WAV paths alike.
8. **`event` messages are sent but ignored by `route`.** `buildEngine` already pushes `{ type: 'event', e }` for every engine event. `onEvent` needs only a case in `route`.
9. **`all: initial` keeps custom properties.** The CSS spec excludes custom properties from `all`. So `--tokk-*` set on `body` or `html` reaches the Shadow DOM through inheritance. Test E8 proves it in Chrome; if it fails, the design is wrong and this document changes first.
10. **The buttons' background differs from the dialog's** (`headerBackground` and `panelBackground`). To keep the default look and give the app one background property, the buttons use `--tokk-bg` with the old header colour as fallback. With a theme, the buttons then have the dialog's background and are told apart by the text-coloured border they already have.
11. **`ears.labels` and `background`.** The first-run flow of Task 22 teaches `click`, `hum`, then `background`. `labels` does not list `background` (the plan). The app can read `ears.sounds.examples` for it. This is said in the doc comment.

## Decisions

### Empty model (`emptyModel`)
A function in `core/classify/knn.ts` next to `trainVectors`, because it builds a `SoundModel` and knows `MODEL_VERSION` and `KNN_K` as `trainVectors` does. It returns version `MODEL_VERSION`, `k` `KNN_K`, the given `sampleRate`, `mean` `[]`, `std` `[]`, `examples` `[]`, `thresholds` `{}`, and no `pitch`. It is not exported from `core/index.ts` (the core's public names stay), and `web/` imports it from the file as it already imports `createEngine` from `core/engine`. `core/index.ts` is checked by `test/public-api.test.ts` (the core runtime names stay five).

### Engine guard
In `classify()` of `core/engine.ts`: when `o.sounds.examples.length` is 0, return no matches before the loop touches the classifier. The model is fixed at `createEngine`, so the check is done once at construction and stored. The tracker and the matcher run as before. Documented in the engine's file comment: "a model without examples is allowed; it recognises no sound".

### `retrainLabel` for `hum` without examples
In `retrainLabel`, in the branch for `hum`: when the kept vectors (all of the model's) and the fresh ones are both empty, skip `trainVectors` and build the result from the model: a copy with `pitch` set to the median of the recordings' pitches when there is at least one, or the old pitch when there is none. The report then has no labels and no pairs, with the warnings. A sound or background label is not changed: its minimum count of examples still comes first. `trainVectors` is not touched.

### Inert hum patterns
`compile()` stores `hum.rise` and `hum.fall` in `out.hum` for any `baselineHz`, including undefined. `checkBaseline` stays. `Matcher.pushContinuous` keeps its early `return []` for an undefined baseline. The doc comment of the file says: a hum pattern is inert without a baseline; give the baseline by building the matcher again (the engine does it when the model changes).

Why not a method such as `setBaseline` on the `Matcher`: the engine's clock and its calibration restart on every model change anyway, so a rebuilt `Matcher` loses no state that a `setBaseline` would keep. A second way to change the baseline would be two paths to test.

P9 and the other pitch tests do not touch the grammar, so they pass unchanged. The new test of requirement 4.5 runs the same rising hum through `runSamples` with and without a baseline and compares the two runs.

### Worker and `route`
- `replaceSounds` calls the existing envelope reset (see finding 6).
- `route` gets two cases. `event`: call `onEvent` unless a dialog is open (`teaching`); a throw goes to `rethrowLater`. `envelope`: after the overlay call, build the public `Envelope` (`t0`, `binMs` = `WEB_ENVELOPE_RESOLUTION_MS`, `min`, `max`) and call `onEnvelope` unless a dialog is open; a throw goes to `console.error`. The same message object feeds the overlay and the app, so the app gets no copy and a doc comment forbids writing to the arrays. A copy would cost 100 small arrays per second for no gain.
- Transfer: `transferListOf` already moves the buffers to the page. Nothing in the page transfers them on.

### `toPageTime`
**Algorithm** (pure module `web/page-time.ts`, no DOM type, no clock). The state is a list of *stretches*. A stretch has the sound time at which it starts (`startT`), a short list of recent delay values with their arrival times, and the current estimate in ms. The module has four operations:
1. *envelope arrived* (arrival time in ms, sound time at the end of the message): the delay value is arrival minus end time times 1000. It enters the current stretch's list. Values older than `WEB_TO_PAGE_TIME_WINDOW_MS` before this arrival are dropped. The estimate is the smallest value left. A monotonic list makes this O(1) per message.
2. *paused or resumed*: `pause()` marks the end of the stretch (the last end time seen is remembered). `resume()` starts a new stretch with `startT` equal to that last end time and a provisional estimate: the page time of the `resume()` call minus that sound time. The first *envelope arrived* of the stretch replaces the provisional estimate (it clears the list, so the provisional value does not stay in the window).
3. *engine rebuilt* (called by the main thread when it posts `record-end`, `record-cancel` or `replaceSounds`): drop all stretches and start an empty one. The envelope messages that were already in flight from the old engine arrive before the first message of the new engine, and they are old-axis values. To keep them out, the page ignores envelope messages from the moment it posts the rebuild until the first envelope whose `t0` is 0 (the Worker restarts the counters, so the first message of the new engine has `t0` 0). This uses a value that is already in the message, not a clock.
4. *to page time* (sound time): choose the last stretch with `startT` at or before the time (the first stretch for an earlier time), return the time times 1000 plus its estimate. Throw when there is no stretch with an estimate. A non-finite time throws a `RangeError`.

**Error model.** Let the true page time of a sample be its capture moment. The message that carries bins up to sound time `e` arrives at the page at the capture moment of the chunk end plus a delay `d` (the hop from the worklet to the Worker to the page, the main thread's queue, and the distance from the last full bin to the chunk end, up to one bin). The smallest `d` over a window of about 100 messages removes queueing delay but not the fixed part. So the estimate is above the true offset by the fixed part of `d`, and the mapped time is late by that. This is what "sound reached the page" means, and the doc comment says it. The error is measured (requirement 6.7).

**Why the arrival of `envelope` messages and not the audio clock.** The other source is `AudioContext.getOutputTimestamp()` with the context time of each chunk. That needs the worklet to post `currentTime` with each chunk, which changes the worklet protocol (the worklet rule: only pass chunks) and works only for the microphone path, not for a WAV `source`. The arrival method needs no change to the worklet, works for all three sources, and the plan says to estimate "from the arrival time of the first chunk and the chunk length". The cost is a bias of a few ms and a dependence on the main thread not being blocked for longer than the window.

**Why a window and not only the first message.** The plan suggests the first chunk. One message can be delayed by a busy page, and the audio clock drifts against `performance.now()`. A window of 2 s follows a drift of 100 ppm within 0.2 ms and still contains about 100 messages.

**Pause.** The worklet stops sending chunks and clears its buffer; up to `WEB_CHUNK_MS` of audio is lost at each pause and each resume. The engine's clock does not advance for it. A sound whose `t` lies in the last bin before a pause (less than `binMs`) would be mapped with the next stretch's offset, which is the pause length too late. This is a known limit (listed under Risks); the sounds of the apps are not near the pause.

### `ears.labels`
`labelsOf(model)` in `web/model.ts`: the distinct labels of `examples` without `BACKGROUND`, plus `HUM_LABEL` when `pitch` exists, sorted by code unit (same comparison as `core/teach.ts`). The getter calls it on the current model, so it follows `adopt`.

### `TeachText`
`web/teach-ui/text.ts` holds the table of requirement 8.1 as a defaults object, the exported type `TeachText` (partial, same keys), the list of allowed placeholders per key, and `resolveTeachText(partial)`, which validates and returns a complete object. Placeholders are `{name}`; the resolver finds every `{...}` in a value and checks the name against the key's list. `fill(template, values)` replaces them. Nothing is interpreted as HTML: the dialog still uses `textContent`. `format.ts` and `state.ts` keep their functions and add a trailing parameter for the texts, defaulting to the defaults, so no existing call or test changes. The default `record` text is built by the existing function (singular for 1); an override is used as written with `{count}` filled.

`mountTeachDialog` takes `text` (resolved) in its options. `listen()` resolves it inside `teach()` before `mountTeachDialog` is called, so a bad `text` rejects before anything opens (requirement 8.3). `teach.html` (Task 17) passes no text and is unchanged.

The visible status lines and buttons that the table lists are the ones an app voice matters for. The rest is diagnostic output (percentages, warnings from the core) or an accessible name; making them overridable would let an app remove the numbers that a user needs to decide to save, and break label-in-name for the Delete button.

### Theming
`web/teach-ui/style.ts` exports the style string, built from the same constants as before, with five replacements: the dialog background uses `var(--tokk-bg, <panelBackground>)`, the buttons' background `var(--tokk-bg, <headerBackground>)`, text colours and the buttons' border `var(--tokk-fg, <text>)`, `progress` `accent-color` `var(--tokk-accent, <waveform>)`, the font family `var(--tokk-font, system-ui, sans-serif)`, and the radius of dialog and buttons `var(--tokk-radius, 4px)`. The 4 px is a new named constant `WEB_TEACH_RADIUS_PX`, because it is today a literal in the style. `all: initial` on the host, the focus outline, the warning colours, the canvas background, the backdrop and the list borders (which use `headerBackground`) are unchanged. The thumbnails use the accent: `teach-dialog.ts` reads `getComputedStyle(dialog).getPropertyValue('--tokk-accent')` once when it draws a thumbnail, trims it, and uses it as the waveform colour when it is not empty (the canvas cannot read a CSS variable by itself). A value that is not a valid colour makes the canvas keep its previous fill style (`fillStyle` ignores an invalid string), which is the default colour set before; the doc comment says to use a valid colour.

Test of "defaults unchanged": step 1 of the tasks freezes the current style string as a literal in `test/teach-text.test.ts` (golden). The test replaces every `var(--tokk-name, fallback)` by its fallback in the new string and compares it to the golden. A second test checks that the five property names are present and that the fallbacks are the `OVERLAY_COLOURS` values. `test/overlay-theme.test.ts` is not touched.

### Start without sounds, in `listen()`
- `opts.sounds` may be `undefined`. The `base` is the pinned fingerprint of `emptyModel(SAMPLE_RATE_MIN_HZ)` when it is, else the fingerprint of the given model, as in Task 16.
- Before the microphone is opened, the stored model is loaded with that base. The throwaway-engine check uses the stored model, the given model, or `emptyModel(SAMPLE_RATE_MIN_HZ)`. After the rate is known (microphone or WAV), the model to start with is chosen: given `sounds` (or its stored replacement), or, when omitted, the stored model if its `sampleRate` equals the rate (requirement 3.3), else `emptyModel(rate)` (with the warning of 3.4). The `init` message and the overlay get that model.
- The rest of `listen()` does not change: `adopt` stores with the same `base`, `teach` passes `sounds` (the current model) to the dialog, `importSounds` checks the model as before.

### Fingerprint of an empty model
`fingerprint(emptyModel(SAMPLE_RATE_MIN_HZ))` with the function of `storage.ts` (FNV-1a of the canonical JSON: keys sorted, no white space). The implementer records the 8 hex digits and a test pins them (a change of `KNN_K` or `MODEL_VERSION` or of the model's fields would change it, and then every stored first-run model is ignored with a warning, which is the right outcome). Note that this value does not depend on the microphone.

### Docs
`integrate.md` gets a section "First run without sounds" (start, `ears.labels`, teach order), a section on events and `toPageTime`, a section on the dialog text and theme, and the changed `hum` line. The power's skill gets the same text for the shared parts, as it has today. Both stay short; the plan's apps read them through the integrator agent.

## Risks and rules
- **Silent app when `sounds` is forgotten.** Stated above. `ears.labels` shows `[]`, the overlay shows no labels, the doc comment names the effect.
- **A rebuild invalidates old times for `toPageTime`.** A handler that stores a `t` and converts it after a Save or an import gets a time from the new axis. The doc comment says to convert inside the handler. The apps do.
- **A sound in the last bin before a pause** maps one pause late (see "Pause"). It is also inside the audio the worklet drops at the pause.
- **A background tab can delay messages.** The smallest-delay rule and the 2 s window absorb short delays; a tab hidden for long gets a larger bound. The apps are used in the foreground, and this is not tested.
- **The mapping is the time the sound reached the page.** It lags the true moment by the input device's latency, which the page cannot read. For the apps (which element was highlighted, a window of 1.2 s) this is small. The measured value says how small.
- **Throwaway engines in `listen()` are now rarely able to fail** (finding 5). They stay: they still reject a bad mode or pattern before a microphone is opened, which is their main job.
- **The accent colour can be unreadable.** The dialog does not check it. The doc comment and `integrate.md` say so (requirement 9.7). The focus outline and the warnings are not themable.
- **`text` could hide a requirement.** Gate reasons other than `needMore` stay default so that the user always sees why a button is disabled.
- **Privacy.** `onEnvelope` gives an app the waveform summary. It never leaves the page through Tokk. The documents tell app code to do the same.
- **Layers.** `web/page-time.ts` and `web/teach-ui/text.ts` have no DOM type, so vitest runs them. `core/` changes are small and pure.
