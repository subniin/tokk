# Devlog

## 2026-11-19

The project scaffold and WAV I/O were built with Kiro CLI from spec `task-01-wav` (`.kiro/specs/task-01-wav/`). The work covers the npm package, TypeScript and Vitest setup, shared types and constants, `core/wav.ts`, and `node/files.ts`.

Task 2 added deterministic test sounds in `core/synth.ts` (seeded `rng`, impacts, tones, noise, `place`, `SYNTH_CLASSES`) from spec `task-02-synth` (`.kiro/specs/task-02-synth/`), with tests in `test/synth.test.ts`.

Task 3 added the FFT, mel filterbank, MFCC and 32-value segment features in `core/dsp/fft.ts`, `core/dsp/mfcc.ts` and `core/features.ts` from spec `task-03-features` (`.kiro/specs/task-03-features/`), with tests in `test/features.test.ts`. Decision: the analysis window is exactly 20 ms at every rate and is zero-padded into an FFT of 2x the window (1024, 2048, 2048, 4096 samples), because a window rounded up to a power of two was 23.2 ms at 44.1 kHz and 21.3 ms at 48 kHz, which broke the 5% rate check.

Task 4 added the chunk-invariant onset segmenter in `core/segment.ts` from spec `task-04-segment` (`.kiro/specs/task-04-segment/`), with tests in `test/segment.test.ts`. Property tests found two rule bugs. P2 (noise only) found `["pink", -20, 16000, seed 3]`: a segment opened at the start of the noise, froze the floor at -70 dBFS for 1.5 s, and a second one opened at 1.795 s. Fix: a 1000 ms calibration period with a 100 ms floor time constant and no onsets. P4 (sample-rate invariance) found `[1, "low", "low", 0, 0, 500, no noise, seed 450386]`: a 6.33 dB one-hop fluctuation in the tail of a single `low` impact split it at 16 and 48 kHz but not at 44.1 kHz. Fix: a two-stage re-onset (candidate at a 3 dB rise, confirmed only if the 70 ms after it hold at least 2.4 dB more energy than the 30 ms before it, margins about 1.1 dB on both sides). Six constants were added to `core/constants.ts`. Test values changed by hand, not the properties: onset step cases became ramps, because the 10 ms window spreads a step over two hops, the 79 ms burst case became 70 ms, the instant-fall case pushes 30 ms instead of 5 ms, every sound starts after the 1 s calibration period, and the P3 and P4 timeouts now scale with `PBT_RUNS`. Properties P2, P3 and P4 pass at `PBT_RUNS=1000`.

Task 11A added two hooks (`pbt-quick` and `public-api-only`, both shell-command hooks on `PostFileSave`) and four steering files (`web-audio.md`, `layers.md`, `units.md`, `privacy.md`) from spec `task-11a-quick-hooks` (`.kiro/specs/task-11a-quick-hooks/`), plus `scripts/check-public-api.ts` and `scripts/pbt-quick.ts`, with tests in `test/scripts.test.ts`. Measured `npm run pbt:quick` (segment suite only, 20 cases): 14.4 s wall time, under the 20 s target. With `PBT_RUNS=100` the same command keeps the value and takes about 62 s. Manual check in Kiro IDE (hooks panel and a save of `core/segment.ts`): not done yet.

Task 5 added the kNN classifier with unknown rejection in `core/classify/knn.ts` (plus `BACKGROUND` in `core/constants.ts`) from spec `task-05-knn` (`.kiro/specs/task-05-knn/`), with tests in `test/knn.test.ts`. Measured: `test/knn.test.ts` takes 6.9 s at `PBT_RUNS=20` and 13.1 s at `PBT_RUNS=100` (95.5 s at 1000). `npm run pbt:quick` (segment and knn files) takes 14.1 s. Deliberate change from the plan: the std floor uses the range over the non-background examples (the statistics set), not over all examples. The background range is often 10 times the real range, so a floor of 0.05 x range over all examples would exceed the real std and undo the exclusion of background from the standardization (review item 11, decision A). Property P6 found a counterexample to the pure k = 3 vote (`high/1003#0` outvoted by two `ring` examples, then `unknown`). Fix: a vector identical to a stored example takes the label of that example (Requirement 5.10). Note for the owner: `pbt:quick` runs 20 cases per property (`QUICK_RUNS`), while plan Task 11A and design 8.2 say 100 (`PBT_RUNS=100` is the default of `npm test`). The script was not changed.

Task 7 added the sound pattern grammar in `core/grammar.ts` (`parsePattern`, `Matcher`, plus `GAP_TOLERANCE_MS` in `core/constants.ts`) from spec `task-07-grammar` (`.kiro/specs/task-07-grammar/`), with tests in `test/grammar.test.ts`. Measured: `test/grammar.test.ts` takes 0.29 s at `PBT_RUNS=100` (0.28 s at 20, 0.39 s at 1000). `npm run pbt:quick` (segment, knn and grammar files) takes 14.1 s. P5 found no counterexample. Decisions where the plan was silent: a gap tolerance of 1e-6 ms for `t = samples / sampleRate` rounding, the matcher gives up at exactly 350 ms for a consecutive candidate and above 1000 ms for a rest candidate, pattern errors are `RangeError`, duplicate patterns are rejected, and continuous `start`/`end` events and `background` sounds are ignored. `core/index.ts` does not exist yet, so the grammar is not exported (Task 8 decides). Also replaced one Korean quotation in `requirements.md` with English.

Task 8 added the engine (`core/engine.ts`: `createEngine`, `runSamples`, with the advance rule `min(now - ENGINE_ADVANCE_MARGIN_MS, openSegmentStart())`), the continuous-tracker socket (`core/continuous/tracker.ts`, no-op until Task 6), the public entry points (`core/index.ts` as `tokk`, `node/index.ts` as `tokk/node`, `package.json` `exports`), `teachFromDir` (`node/teach.ts`: segments as examples, background windows capped at 200, calibration warnings, `hum` folder skipped, leave-one-out report) and `expectEvents` (`node/expect.ts`) from spec `task-08-engine` (`.kiro/specs/task-08-engine/`), with tests in `test/engine.test.ts`, `test/teach.test.ts` and `test/public-api.test.ts`. Constants added: `ENGINE_ADVANCE_MARGIN_MS`, `LOO_MIN_EXAMPLES_PER_LABEL`, `CONFUSED_PAIR_MIN_RATE`; `trainVectors` got an optional `minExamplesPerLabel`. P1 (count preservation) drove seven rounds of changes, each recorded in the specs. (1) At 15 dB SNR the one-hop onset rule found 2 to 7 of 30 impacts (`[44100, "mid", 1, 100, 0, 15, 1]`: the 10 ms window spreads a step over two hops); a two-hop rise fixed that but P2 then found `["pink", -20, 16000, 7]`. (2) A model trained without noise rejected noisy impacts (`[44100, high, 1, gain -9, SNR 28, seed 98792]`), so P1 models are now trained with 15 to 30 dB room noise. (3) A test bug: the SNR was set from the first clip only; it now uses the quietest clip. (4) Owner decisions narrowed the ranges: SNR >= 20 dB, then gaps 210 to 600 ms (P1) and 440 to 600 ms (P1b), just above the uncut segment lengths of `mid` (205 ms) and `ring` (430 ms). (5) Segmenter rules (Task 4) are now: onset at level > floor + 16 dB with a 3 dB one-hop step within the last 60 ms (`ONSET_ABOVE_FLOOR_DB` 16, `ONSET_RISE_DB` 3, new `ONSET_RISE_SPAN_MS` 60; margins: worst impact at 20 dB SNR +1.67 dB, worst P2 noise -1.97 dB), and re-onset candidates in a queue, confirmed when the 70 ms after hold 4 dB and the first 15 ms 3 dB more energy than the 30 ms before (`REONSET_CONFIRM_DB` 2.4 to 4, new `REONSET_CONFIRM_EARLY_MS` 15 and `REONSET_CONFIRM_EARLY_DB` 3), after `[44100, "low", 2, 300, 0, 26, 468767]` (a tail fluctuation confirmed by the next hit) and isolated `low` tails split at 2.84 and 3.04 dB in noise. One Task 4 ramp test input changed from 5 to 2.5 dB per hop (expected result unchanged). `test/segment.test.ts` passes at `PBT_RUNS=300` with fast-check seeds 101 and 202. (6) Classifier (Task 5): labels among the k = 3 nearest are tried in vote order and the first within its own threshold wins, after `[48000, "high", 3, 460, 0, 20, 984357]` and `[48000, "high", 2, 264, 0, 20, 7]` (`ring` won the vote and failed its 4.96 limit while `high` passed 9.17); P6, P7, P8 pass at `PBT_RUNS=300` with seeds 101 and 202. (7) Because thresholds come from 10 examples, an uncut impact can still land just outside them in one noise realization (`[44100, "mid", 2, 214, 0, 28, 274038]`: 7.05 against 7.04), so P1 and P1b became statistical acceptance tests: a fixed `rng` case set (150 cases by default, 300 when `PBT_RUNS >= 300`), pass at >= 98 % exact, no over-count, no wrong label, every miss an `unknown`. Measured at 300 cases: P1 99.7 %, P1b 99.7 % (one `unknown` each), 0 over-counts, 0 wrong labels; at 150 cases both 100 %. Known limit and follow-up: a hit before the previous segment ends naturally cuts it and the cut segment can be `unknown`; robustness to truncated segments is decided after experiments E1 and E3. Measured runtimes (PBT_RUNS=100): `test/engine.test.ts` 6.4 s (9.6 s at 1000, which uses 300 cases), `test/teach.test.ts` 5.2 s, `test/public-api.test.ts` 1.6 s, `test/knn.test.ts` 14.2 s, `test/segment.test.ts` 60.0 s; `npm test` 60.5 s (221 passed, 5 todo); `npm run pbt:quick` 14.0 s. The five hum tests stay `test.todo` until Task 6.
